# API Vocabulary Governance

`docs/standards/api-vocabulary/lotus-risk-api-vocabulary.v1.json` is generated by:

```powershell
python scripts/api_vocabulary_inventory.py --output docs/standards/api-vocabulary/lotus-risk-api-vocabulary.v1.json
```

`make api-vocabulary-gate` validates that the generated inventory is current.

## Context-Aware Semantic IDs

Semantic IDs are not leaf-name aliases. Fields such as `status`, `state`, `reason`, and `type`
must use the domain context carried by their schema and field path.

Examples:

1. health response `status` is `lotus.health_status`,
2. readiness response `status` is `lotus.readiness_status`,
3. dependency row `status` is `lotus.dependency_runtime_status`,
4. trust dependency signal `status` is `lotus.trust_dependency_status`,
5. calculation supportability `state` is `lotus.calculation_supportability_state`,
6. calculation supportability `reason` is `lotus.calculation_supportability_reason`,
7. risk-free context `reason` is `lotus.risk_free_context_reason`,
8. period `type` is `lotus.period_type`.

The old generic IDs `lotus.status`, `lotus.state`, `lotus.reason`, and `lotus.type` are intentionally
not used for multiple incompatible concepts. If a new API field has one of those leaf names, update
the generator's governed contextual mapping and focused tests rather than letting the fallback
semantic ID collapse distinct meanings.
